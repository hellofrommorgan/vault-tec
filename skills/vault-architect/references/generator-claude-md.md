# CLAUDE.md Master Generator

Generate the CLAUDE.md system prompt for a vault by composing 8 feature blocks, adapted to user domain and preferences. The generated file is DIRECTIVES — it tells Claude what to DO, not why. No research citations in the output. No explanatory prose. Terse, enforceable rules.

## Generation Protocol

1. Read all 8 feature blocks from this references/ directory:
   - feature-structure.md → Architecture section
   - feature-navigation.md → Navigation section
   - feature-processing.md → Processing section
   - feature-quality.md → Quality section
   - feature-domains.md → Domains section
   - feature-intelligence.md → Intelligence section
   - feature-personality.md → Identity section
   - feature-runtime.md → Runtime section (NEW in v0.7.0)
2. For each block, adapt its content to the user's:
   - Primary domain(s)
   - Communication style (formal/casual/technical)
   - Scale expectations (small personal vault vs. large research system)
   - Processing preferences (structured vs. emergent)
3. Compose them into a single CLAUDE.md following the structure below
4. Write the generated file to the vault root
5. Compute a config fingerprint and embed it

## Config Fingerprint Algorithm

The fingerprint ensures health checks can detect when CLAUDE.md is stale relative to vault evolution.

**Variables to hash** (concatenated in this order, pipe-delimited):
1. VAULT_NAME
2. PRIMARY_DOMAIN
3. TONE (formal|casual|technical)
4. PIPELINE_DEPTH (full|standard|minimal)
5. MIN_LINKS (default: 2)
6. MOC_THRESHOLD (default: 50)
7. HEALTH_FREQUENCY (default: weekly)
8. GUARDRAIL_STRICTNESS (default: standard)
9. SESSION_FORMALITY (default: structured)
10. DOMAIN_COUNT (integer)
11. NOTE_COUNT_BUCKET (small:<50|medium:50-200|large:>200)

**Algorithm**: SHA-256 of `"VAR1|VAR2|...|VAR11"`. Truncate to first 16 hex characters for display.

**Example**: For vault "neuro-research", domain "neuroscience", tone "technical", full pipeline, defaults:
`SHA-256("neuro-research|neuroscience|technical|full|2|50|weekly|standard|structured|3|medium")` → first 16 chars → `Config fingerprint: a7b3c9d2e1f45678`

## CLAUDE.md Design Principles

The generated CLAUDE.md must follow these principles:

- **Directives, not documentation**: Write "Do X" not "The reason for X is..."
- **Specific and enforceable**: "Every atomic note must have ≥2 wiki-links" not "Notes should be well-connected"
- **Reference by pointer, not duplication**: "Read self/identity.md for your persona" not [inline persona copy]
- **No research citations in output**: Research backing lives in vault-methodology skill references. The CLAUDE.md says WHAT, not WHY.
- **Only include what Claude can't infer**: Don't explain what YAML is. DO specify which fields are required.
- **Staleness-aware**: Include a config fingerprint so health checks can detect when CLAUDE.md is out of date relative to vault evolution.

## CLAUDE.md Structure

```
# [Vault Name] — Agent System Prompt

> Generated by vault-tec v0.7.0
> Last generated: [DATE]
> Config fingerprint: [first 16 hex chars of SHA-256]

## Identity

Read `self/identity.md` at every session start. It defines your persona, voice, expertise, and communication style for this vault.

Read `self/methodology.md` for processing rules. Read `self/goals.md` for current priorities.

Log every change to self/ files in `self/evolution-log.md`.

## Architecture

[From feature-structure.md — adapted. Directives only:]
- Three-space model: self/ (identity, slow-change), notes/ (knowledge, steady-growth), ops/ (operations, high-churn)
- Required YAML frontmatter fields for every note in notes/: type, domain, created, status, connections
- Note types: atomic-note, moc, source-note, reflection, seed-task, session-log, domain-entry
- Templates in templates/ are the single source of truth for each note type's schema

## Navigation

[From feature-navigation.md — adapted. Directives only:]
- MOC hierarchy: _MOC-Master → _MOC-[Domain] → _MOC-[Topic]
- Every note must have ≥{{MIN_LINKS}} outgoing [[wiki-links]] in body text
- Create a topic MOC when a cluster exceeds {{MOC_THRESHOLD}} notes
- Organize MOC entries by conceptual relationship, not alphabetically

## Processing

[From feature-processing.md — adapted. Directives only:]
- Pipeline: Record → Reduce → Reflect → Reweave → Verify → Rethink
- Session rhythm: Orient (read self/, check ops/inbox/) → Work → Integrate (log session, update MOCs)
- Status lifecycle: seed (raw) → growing (processed, connected) → evergreen (verified, challenged)
- 6R contracts enforced per phase (see feature-processing.md for I/O specs)

## Quality

[From feature-quality.md — adapted. Enforceable rules only:]
- Every claim in an atomic note must reference a source via the `sources:` frontmatter field
- Every note write to notes/ must pass schema validation (hook-enforced)
- Never modify self/ files without appending an entry to self/evolution-log.md
- Never create a note in notes/ without complete YAML frontmatter
- Never leave a note with 0 wiki-link connections (incoming or outgoing)
- Never place knowledge notes in ops/ or operational files in notes/
- Never delete notes without explicit user confirmation
- Set the `confidence:` field on every atomic note (low|medium|high) — do not default to "high"
- When uncertain about a claim, use `confidence: low` and note the uncertainty in the body
- Hook enforcement: Write hooks WARN on violations (not silent pass)

## Runtime

[From feature-runtime.md — NEW in v0.7.0:]
- Track vault metabolic rates per space (self: slow, notes: steady, ops: fluctuating)
- Monitor identity stability via self/ change frequency
- Reconciliation: fast (write-time validation), medium (session-start health snapshot), slow (monthly full audit)
- Maintain desired-state targets: zero orphans, {{TARGET_ORPHAN_RATE}}% orphan tolerance, {{REWEAVE_STALENESS_DAYS}} day reweave window
- Report gaps between actual and desired state at session start

## Domains

[From feature-domains.md — adapted. Rules only:]
- Each domain has its own subdirectory under notes/domains/
- Every note has exactly one primary domain in frontmatter
- Cross-domain connections use wiki-links, not dual-domain assignment
- New domains require: directory, domain MOC, domain-entry note, link from _MOC-Master

## Commands

### Processing
- `/reduce [note]` — Extract core insight, draft atomic structure
- `/reflect [note]` — Find connections, suggest wiki-links
- `/reweave [note]` — Update with context from linked notes
- `/verify [note]` — Schema compliance + link integrity check
- `/rethink [note]` — Challenge assumptions, find counter-evidence
- `/pipeline [note]` — Full 6R sequence (each R in fresh context)

### Navigation
- `/graph` — Connection topology: nodes, edges, hubs, orphans, clusters
- `/stats` — Note count, connection density, status distribution
- `/next` — Highest-value next action based on current vault state

### Operations
- `/seed [topic]` — Queue a research seeding task in ops/tasks/
- `/tasks` — List active task queue
- `/remember` — Mine current session for insights worth preserving
- `/learn [topic]` — Quick research burst on a specific concept
- `/validate` — Schema validation across all notes

### Maintenance (v0.7.0)
- `/vault-tec:reweave` — Surface stale notes, guided reweave workflow
- `/vault-tec:friction` — Diagnose architectural friction patterns
- `/vault-tec:runtime` — Identity dashboard, metabolic rates, gap report
- `/vault-tec:triggers` — Run test suite (unit/integration/regression)
```

## Adaptation Rules

When generating CLAUDE.md:
- **Domain specificity**: Replace generic examples with domain-specific ones. If the vault is about neuroscience, examples should reference neurons, not generic "concepts."
- **Voice calibration**: Match the user's communication style. Academic users get formal language. Builders get direct, action-oriented language.
- **Scale adaptation**: Small vaults don't need `/graph`. Large vaults need stronger MOC discipline. Only include commands the vault's scale warrants.
- **Feature selection**: Not every vault needs every feature block. If the user doesn't want multi-domain support, omit the Domains section. If they prefer emergence over structure, lighten the Schema requirements.
- **Runtime inclusion**: Always include the Runtime section in v0.7.0+. It's the foundation for session bookends and reconciliation.
- **Staleness tracking**: After generating, compute the config fingerprint using the algorithm above. Embed as `Config fingerprint` in the header.
